# AGENTS.md

## Repository overview

Oral History Digital is a multi-project platform for curating and researching audiovisual interviews. Rails serves HTML and JSON; React is mounted through react-on-rails and bundled by Shakapacker/Webpack. The application uses MariaDB/MySQL, Solr search, and Delayed Job.

Read nearby code before choosing a pattern. This codebase mixes older Redux and controller code with newer hooks and services.

## Non-negotiable invariants

- Before changing application code, inspect the affected code and identify the relevant architecture, authorization, project scope, and tests. Then make the smallest change that satisfies the task.
- Do not commit, push, merge, rebase, reset, stash, switch branches, tag, or otherwise alter repository history unless the developer explicitly requests it. Do not stage files unless needed for an explicitly requested Git operation. Use read-only commands such as `git status`, `git diff`, and `git log` freely for inspection.
- When explicitly asked to create a commit:
    - Do not add `Co-authored-by:` trailers.
    - Do not add `Generated with Claude Code`, `Generated by AI`, or similar attribution lines.
    - Keep the commit message short. A subject line alone is usually sufficient.
    - Add a commit body only when it conveys useful information not apparent from the diff, such as a non-obvious cause, constraint, or rejected alternative. Do not use the body merely to summarize the changes.
- Do not overwrite, revert, or discard existing developer changes unrelated to the task. Treat pre-existing working-tree modifications as intentional unless clearly shown otherwise.
- Preserve project isolation. Resolve the request project through `current_project` (`app/controllers/application_controller.rb`) and scope project-owned records through that project or an existing project-aware policy scope. Check related records and cached data for cross-project exposure.
- Preserve Pundit checks. `ApplicationController` verifies `authorize` after non-index actions and `policy_scope` after index actions; follow existing explicit exceptions only when their access behavior is justified. Policies receive `ProjectContext` with the user and current project.
- Preserve `archive_id` as the public interview identifier in routes and API references. Numeric model IDs are internal; inspect existing lookup and authorization behavior before changing an interview query.
- Preserve current response contracts, locale/project-aware URLs, and the Rails/React domain-routing agreement. Changes to `OHD_DOMAINS` or `PASSWORD_REGEX` must update both `config/initializers/constants.rb` and `app/javascript/modules/constants/index.js`.
- Cover changes to authentication, authorization, project scope, uploads, domain routing, and exports with focused tests, including denied and cross-project cases where applicable.
- Do not touch `config/locales` or `config/translations` unless the task explicitly requires updating exported translation snapshots. Runtime application translations live in the database through `TranslationValue`; these files are not the primary translation source. Treat them as exported/setup snapshots, not as the place to add or edit normal UI translations.

## Where code belongs

- Rails entry points: `config/routes.rb`, `app/controllers`, `app/policies`. Keep request parsing, authorization, and rendering in controllers. Put multi-step workflows in focused `app/services` classes; put complex joins, reporting, and reusable query composition in `app/repositories`. Keep simple scopes on models.
- Data and responses: `app/models`, `db/migrate`, `db/schema.rb`, `app/serializers`. JSON often uses ActiveModelSerializers through existing controller helpers and envelope fields. Reuse the local response shape and serializer rather than changing clients implicitly.
- Background work and search: `app/jobs`, `ApplicationJob`, model `searchable` blocks, and `config/sunspot.yml`. Active Job uses `:delayed_job`; search uses Sunspot/Solr. Preserve queue and indexing behavior when changing data lifecycles.
- React entry points: `app/javascript/packs/application.js` registers `startup/App.js`; `startup/archiveStore.js` creates the Redux store; `modules/routes/RouteDivider.js` selects routes by project/domain. Put UI, hooks, and tests near their domain in `app/javascript/modules`; put styles in `app/javascript/stylesheets`.
- Deployment references: `Dockerfile`, `docker-compose.yml`, `.devcontainer/`, `config/deploy/`, and `doc/docker_instance_setup.md`. Do not infer production operations from the development container.

Before introducing a new service, repository, helper, hook, serializer, component, or utility, search for an existing implementation of similar behavior. Prefer extending an established local pattern over creating a parallel abstraction.

## Development workflow

- Use the development container for Ruby, Rails, Node, and Yarn commands, as the `vscode` user in `/workspace`. The devcontainer setup and startup hooks install dependencies, prepare the database, and start Rails/Webpack; see `.devcontainer/README.md` and `.devcontainer/scripts/`.
- When operating from the host, identify the running app container from Compose service labels rather than assuming a fixed container name. One supported command is:

```sh
docker ps \
  --filter label=com.docker.compose.project=dev \
  --filter label=com.docker.compose.service=app \
  --format '{{.Names}}'
```

Then run commands inside it as the `vscode` user:

```sh
docker exec -u vscode <container-name> sh -lc 'cd /workspace && <command>'
```

If Docker group access is missing, use `sg docker -c 'docker ...'`.

- If manual setup is needed inside the container, use:

```sh
bundle install
yarn install --frozen-lockfile
bin/rails db:prepare
```

- For schema changes, add a reversible migration, run `bin/rails db:migrate`, and update `db/schema.rb`. Do not edit the generated schema alone.
- For manual development startup, run the `Procfile` processes with:

```sh
bin/start_app
bin/start_search
bin/shakapacker-dev-server
```

- When asset compilation is affected, verify the production frontend build with:

```sh
RAILS_ENV=production bin/shakapacker
```

Frontend CI runs this command in `.github/workflows/jest.yml`. The Docker image uses a separate `assets:precompile` path.

## Architecture and implementation conventions

- Follow the affected feature's conventions before adding a service, repository, hook, serializer, or other abstraction. Service constructors vary; do not impose one signature on unrelated classes.
- Keep Pundit policy changes aligned with the records they protect. Inspect the existing scope for the affected resource rather than assuming direct `project_id` ownership; some records are scoped indirectly through related records.
- Preserve `/:locale` and `/:project_id/:locale` routing and dedicated archive-domain routes in `config/routes.rb`. React Router has corresponding route shapes in `app/javascript/modules/routes`. Use existing route helpers and hooks instead of manually assembling paths where an established mechanism exists.
- Preserve existing Redux/thunk and API-middleware flows when changing legacy code.
- For new frontend code, prefer hooks where possible, including `useSelector`, `useDispatch`, route hooks, and focused SWR/`useSWRImmutable` hooks.
- Do not create new legacy `connect` / `mapStateToProps` / `mapDispatchToProps` container wrappers. Preserve existing containers unless the task explicitly includes their refactor.
- Avoid feature-wide state migrations for task-scoped work.
- Write new frontend code in JavaScript (`.js`/`.jsx`), not TypeScript.
- Preserve component PropTypes, semantic controls, labels, and keyboard/focus behavior.
- Do not add a parallel frontend build stack, state-management library, or broad component rewrite for a task-scoped change.
- Preserve Globalize model translations and project/locale context.
- Runtime UI strings are stored as `TranslationValue` records and exposed to React through the existing translation state and `modules/i18n`. Do not move runtime translations into locale files.
- Preserve existing upload validation, MIME checks, malware scanning, and authorization in upload flows. Inspect the affected upload path before changing it.
- Keep secrets, tokens, session data, personally identifying information, and private interview content out of logs.

## Testing and verification

- Run the narrowest relevant tests during implementation, then the appropriate broader suite before considering the task complete. Report what actually ran and any environment limitation.
- Rails uses Minitest in `test/`; system tests use Capybara/Selenium.

Focused Rails test:

```sh
bundle exec rails test test/path_to_test.rb
```

Backend suite:

```sh
bundle exec rails test -v test
```

System tests:

```sh
bundle exec rails test -v test/system
```

`bin/test` runs the combined Rails test pipeline and supports `RETRY=true` and `HEADLESS=true`.

- React tests are colocated `*.test.js`/`*.test.jsx` files under `app/javascript`; Jest uses jsdom.

Focused frontend test:

```sh
yarn test --runInBand --runTestsByPath app/javascript/path/to/file.test.jsx
```

Frontend suite:

```sh
yarn test
```

- Use React Testing Library for new component interactions where practical; follow adjacent tests for existing modules.
- Run `yarn lint` for changed frontend code.
- `.eslintrc.js` defines lint rules; `.prettierrc` uses single quotes, four-space JavaScript indentation, and sorted imports. Limit formatting to touched code.
- Test policy/controller changes for authorization, policy scope, project scope, and response shape.
- Test service/repository changes for business behavior, query correctness, and project isolation.
- Test UI changes for visible behavior and interaction.
- Test locale/project paths when routing changes.
- Run migration checks when schema behavior changes.
- Run the production Shakapacker build when frontend asset compilation is affected.
- Do not claim a command passed unless it completed successfully.

## Things to avoid

- Do not rely on route parameters alone for authorization or project membership.
- Do not replace `archive_id` with numeric IDs in public interview behavior.
- Do not bypass Pundit verification or weaken upload validation to make a request pass.
- Do not change JSON envelopes or cross-layer constants on one side only.
- Do not add runtime translations to `config/locales`.
- Do not treat `config/translations` as the runtime translation source.
- Do not introduce a new frontend stack, TypeScript migration, or broad Redux conversion without an explicit request.
- Do not rewrite large files for style.
- Do not add abstractions without a current use.
- Do not undo unrelated developer changes.

## Definition of done

- Confirm the affected route, policy, project scope, and external identifiers still agree.
- Update tests at the changed layer.
- Run focused checks and the relevant broader suite when feasible.
- Check downstream effects appropriate to the change, including schema, translations, serializers/API contracts, background jobs, and search indexing when affected.
- Review `git status` and `git diff` for unintended files.
- Report changed behavior, tests run, failures, skipped checks, and remaining limitations accurately.
- Include a proposed short commit message in the final report using fix:(scope): concise description and a short description of the changes. Do not create the commit unless explicitly requested.
